# 🧮 Mini NPU Simulator

AI가 이미지를 판별할 때 쓰는 **MAC(Multiply-Accumulate) 연산**을 직접 구현한 Python 콘솔 프로그램입니다.
십자가(Cross)와 X 모양 필터를 숫자 배열로 만들고, 입력 패턴과 곱하고 더한 점수로 어떤 모양인지 판정합니다.
3×3부터 25×25까지 크기를 바꿔 가며 연산 시간이 어떻게 늘어나는지도 측정합니다.

> Codyssey 올인원 1기 입학 연수 — 미션 3 「AI가 계산하는 방식을 흉내 내는 작은 계산기 만들기」

## 4. 구현 요약

### 4-1. 데이터 구조

패턴과 필터는 **리스트 안에 리스트가 들어 있는 2차원 리스트**로 저장합니다.
`matrix[행][열]`로 특정 위치의 값을 읽고 쓰며, `get_value` / `set_value` 함수로 감쌌습니다.
크기는 정해 두지 않고 `n`을 받아 만들기 때문에 3×3, 5×5, 13×13, 25×25 모두 같은 코드로 처리합니다.

### 4-2. MAC 연산

```python
def mac(pattern, filter_matrix):
    n = len(pattern)
    total = 0.0
    for i in range(n):              # 행
        for j in range(n):          # 열
            total += pattern[i][j] * filter_matrix[i][j]
    return total
```

- NumPy 없이 **이중 반복문**으로 같은 위치의 값끼리 곱해 `total`에 누적합니다.
- 곱셈·덧셈이 정확히 **N × N 번** 일어납니다. 이 숫자가 성능 표의 "연산 횟수"입니다.

### 4-3. 라벨 정규화

`data.json`에는 같은 뜻의 라벨이 여러 표기로 섞여 있습니다.

| 위치 | 원래 표기 | 표준 라벨 |
|---|---|---|
| `expected` 값 | `+` | `Cross` |
| `expected` 값 | `x` | `X` |
| 필터 키 | `cross` | `Cross` |
| 필터 키 | `x` | `X` |

`normalize_label()`이 앞뒤 공백을 지우고 소문자로 바꾼 뒤 표준 라벨로 변환합니다.
판정 결과도 `Cross` / `X`로 나오므로, **같은 기준끼리 비교**해야 PASS/FAIL이 올바르게 나옵니다.
정규화하지 않으면 판정 `Cross`와 expected `+`를 비교해 모든 케이스가 FAIL이 됩니다.

### 4-4. 동점 처리 정책 (epsilon)

```python
EPSILON = 1e-9

def judge(score_a, score_b, label_a, label_b):
    if abs(score_a - score_b) < EPSILON:
        return "UNDECIDED"
    ...
```

- 실수 계산은 `0.1 + 0.2 = 0.30000000000000004`처럼 아주 작은 오차가 생깁니다.
- 그래서 `==` 대신 **두 점수의 차이가 1e-9보다 작으면 동점(UNDECIDED)**으로 봅니다.
- 동점은 Cross도 X도 아니므로 expected와 다르게 되어 **FAIL**로 처리합니다.

### 4-5. 모드 2 검증 순서 (케이스 단위 FAIL)

패턴 하나마다 아래 순서로 검사하고, 문제가 있으면 **그 케이스만 FAIL로 기록하고 다음 케이스로 넘어갑니다.** 프로그램은 멈추지 않습니다.

1. 키 형식 — `size_{N}_{idx}` 모양인지, N이 숫자인지
2. 스키마 — `input`, `expected`가 있는지
3. 필터 존재 — `size_N` 필터가 로드되었는지
4. 크기·값 — `input`이 숫자로 된 N×N인지
5. 라벨 — `expected`가 `+` / `x` 등 알 수 있는 값인지
6. MAC 연산 → 판정 → expected와 비교

파일이 없거나 JSON 문법이 깨진 경우에도 `try / except`로 잡아 안내 문구만 출력하고 메뉴로 돌아갑니다.

### 4-6. 모드 1 입력 검증

한 줄씩 입력받아 `split()`으로 나눈 뒤 다음을 검사하고, 잘못된 줄만 다시 입력받습니다.

| 오류 | 안내 문구 |
|---|---|
| 숫자 개수가 3개가 아님 | `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.` |
| 숫자로 바꿀 수 없음 (`a`) | `입력 형식 오류: 숫자만 입력하세요.` |

정확히 3줄을 받을 때까지 반복하므로 행 수도 항상 3으로 맞춰집니다.

### 4-7. 성능 측정

```python
start = time.perf_counter()
for _ in range(10):
    mac(pattern, filter_matrix)
end = time.perf_counter()
avg_ms = (end - start) * 1000 / 10
```

- 입력·출력·파일 읽기는 빼고 **MAC 함수 호출 구간만** 잽니다.
- 한 번은 너무 빨라 측정값이 흔들리므로 **10회 반복 후 평균**을 냅니다.
- 측정용 데이터는 패턴 생성기(`make_cross`, `make_x`)로 크기만 바꿔 만들어, 모양이 아닌 **크기의 영향만** 비교합니다.

## 6. 결과 리포트

### 6-1. 실패 원인 분석

실패 원인은 **데이터/스키마 문제 → 로직 문제 → 수치 비교 문제** 순서로 나눠 진단했습니다.

총 6개 중 3개가 FAIL이며, 3개 모두 **수치 비교(동점) 문제**입니다.
데이터/스키마 문제(키·크기·라벨)는 0건, 로직 문제(MAC 계산 오류)도 0건입니다.

| 케이스 | 수학적 계산 | 실제 float 결과 | 판정 |
|---|---|---|---|
| `size_5_1` (X 입력) | Cross: 가운데 1칸 × 0.9 = **0.9** / X: 0.1 × 9칸 = **0.9** | 0.9 vs 0.8999999999999999 | UNDECIDED → FAIL |
| `size_13_2` (십자가 입력) | Cross: 0.3 × 25칸 = **7.5** / X: 가운데 1칸 × 7.5 = **7.5** | 7.499999999999997 vs 7.5 | UNDECIDED → FAIL |
| `size_25_1` (X 입력) | Cross: 가운데 1칸 × 4.9 = **4.9** / X: 0.1 × 49칸 = **4.9** | 4.9 vs 4.899999999999999 | UNDECIDED → FAIL |

**① 원인: 필터 값이 "일부러" 동점이 되도록 설계되어 있음**
- 세 케이스 모두 필터의 가운데 칸 값(0.9, 7.5, 4.9)이 반대쪽 필터의 합과 정확히 같게 맞춰져 있습니다.
- 그래서 수학적으로는 두 점수가 완전히 같습니다. 이 데이터는 **동점 처리 정책을 시험하기 위한 케이스**입니다.

**② 왜 숫자가 미세하게 다른가: 부동소수점 오차**
- 컴퓨터는 0.1, 0.3 같은 소수를 2진수로 정확히 표현하지 못해 아주 작은 오차가 있습니다.
- 이 값을 9번, 25번, 49번 더하면 오차가 쌓여 `0.8999999999999999`처럼 됩니다.
- 반면 한 칸만 곱한 쪽(0.9, 7.5, 4.9)은 오차가 쌓이지 않아 두 값이 1e-15 정도 차이 납니다.

**③ epsilon 정책이 없었다면**
- `score_a > score_b`로 단순 비교하면 size_5_1은 Cross, size_13_2는 X, size_25_1은 Cross로 판정됩니다.
- 이것은 실제 유사도 차이가 아니라 **계산 오차가 결과를 정한 것**이라 믿을 수 없는 판정입니다.
- 그래서 `|A - B| < 1e-9`이면 동점(UNDECIDED)으로 보고, 과제 규칙대로 expected와 다르므로 FAIL 처리했습니다.

**④ 다른 문제는 왜 0건인가**
- 라벨: expected의 `+`/`x`, 필터 키의 `cross`/`x`를 `normalize_label()`로 `Cross`/`X`로 통일했기 때문에 표기 차이로 인한 FAIL이 없습니다.
- 스키마: 키에서 N을 추출해 `size_N` 필터를 고르고, 패턴이 N×N인지 검증했습니다. 이번 데이터는 모두 크기가 맞았습니다.
- 로직: 동점이 아닌 3개 케이스(5_2, 13_1, 25_2)는 모두 expected와 같게 판정되어 MAC 계산이 올바름을 확인했습니다.

**⑤ 진단 순서 정리**
| 분류 | 확인 방법 | 이번 결과 |
|---|---|---|
| 데이터/스키마 | 키 형식, input/expected 존재, N×N 크기, 라벨 | 0건 |
| 로직 | 동점이 아닌 케이스가 expected와 맞는지 | 0건 |
| 수치 비교 | 두 점수 차이가 1e-9 미만인지 | 3건 (의도된 동점) |

### 6-2. 성능 표와 시간 복잡도

```text
크기          평균 시간(ms)   연산 횟수(N²)
----------------------------------------
3×3              0.0009             9
5×5              0.0016            25
13×13            0.0069           169
25×25            0.0230           625
```

- MAC 연산은 N×N 칸을 한 번씩 방문하므로 곱셈·덧셈이 **N² 번** 일어납니다. 그래서 시간 복잡도는 **O(N²)** 입니다.
- 5×5 → 25×25로 한 변이 **5배**가 되면 연산 횟수는 25 → 625로 **25배(5²)** 늘어납니다.
- 측정 시간도 0.0016 → 0.0230 ms로 약 **14배** 늘어 N²에 가깝게 증가했습니다.
- 13×13 → 25×25(연산 3.7배)에서도 시간이 약 3.3배 늘어, **연산 횟수와 시간이 거의 비례**합니다.
- 3×3처럼 작은 크기는 반복문 시작, 함수 호출 같은 고정 비용 비율이 커서 정확히 비례하지는 않습니다.
- 측정값은 컴퓨터 상태에 따라 실행할 때마다 조금씩 다르지만, **늘어나는 비율**은 비슷하게 유지됩니다.
- 실제 AI 모델은 큰 필터를 수천 개 사용하므로 이런 연산이 수억 번 필요합니다. CPU는 이를 하나씩 차례로 처리하지만, NPU는 많은 MAC을 **동시에(병렬로)** 처리해 시간을 줄입니다.

### 6-3. (보너스) 2차원 vs 1차원 비교

| 크기 | 2차원(ms) | 1차원(ms) | 개선 |
|---|---|---|---|
| 3×3 | 0.0007 | 0.0006 | 15.9% |
| 5×5 | 0.0014 | 0.0009 | 38.3% |
| 13×13 | 0.0069 | 0.0051 | 25.7% |
| 25×25 | 0.0243 | 0.0206 | 15.1% |

- 1차원 리스트는 `pattern[i][j]`(두 번 찾기) 대신 `pattern[k]`(한 번 찾기)로 접근하고, 반복문도 1개로 줄어 조금 빨라졌습니다.
- 하지만 연산 횟수는 여전히 N²이므로 **복잡도는 O(N²)로 같습니다.** 줄어든 것은 한 번 연산할 때 드는 비용(상수)입니다.

## 8. 배운 점

- 컴퓨터가 "모양을 본다"는 것은 결국 **숫자 배열끼리 곱하고 더하는 계산**이라는 것을 직접 확인했습니다.
- 같은 뜻의 데이터가 다르게 표기될 수 있어 **비교 전에 표준화**가 필요합니다.
- 실수는 `==`로 비교하면 위험하고, **허용오차 기준**을 정해야 합니다.
- 오류가 있는 데이터가 하나 섞여 있어도 **전체 프로그램은 멈추지 않게** 만들어야 합니다.
